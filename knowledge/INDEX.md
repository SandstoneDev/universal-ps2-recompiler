## hardware (the PSP (and PS2) hardware as measured)

- [Coroutine stacks must live inside the PSP thread's own stack](hardware/coroutine-stacks-in-thread-stack.md) - Guest threads run as coroutines; their stacks must be carved from the stack of the PSP thread that runs them.
- [Exit order](hardware/exit-order.md) - Leave the game in a fixed order: audio and Media Engine, GE, counters, kernel module, then exit; log each step first.
- [The file size is recorded on close](hardware/fat-size-recorded-on-close.md) - A log that is only flushed stays empty after a crash: open, append, write and close on every commit.
- [Free memory on the 64 MB models](hardware/free-memory-64mb-models.md) - Plan with about 51 MB for the program in large-memory mode; PPSSPP reports about 5 MB more than the device.
- [GE 3D back-end: batch on the CPU side, key caches by content](hardware/ge-3d-backend-costs.md) - Convert the game's vertex streams once per mesh into GE sub-lists, cache them by content, batch the per-mesh CPU work, write commands into the open list and kick rarely; per-mesh CPU cost on the PSP is 4x PPSSPP's.
- [Measuring the GE: the busy sampler lies, use a serial probe](hardware/ge-busy-sampler-pitfall.md) - Polling the GE's draw-sync state reports "drawing" while a list is merely open; measure GE time by replaying one captured frame with the CPU idle.
- [GE display-list safety](hardware/ge-display-list-safety.md) - A malformed display list freezes the console; guard every list, keep caches coherent and key caches by content.
- [Log writes and disc reads as frame-time spikes](hardware/hitches-log-and-disc.md) - Keep a frame-time histogram; buffer the log and read the disc asynchronously, answering the game's polls.
- [A kernel module must export module_stop](hardware/kernel-module-export-module-stop.md) - Without an exported module_stop the kernel never runs it; unloading then frees handlers the kernel still uses.
- [The 64 MB mode is a request: check it at start; use the volatile 4 MB carefully](hardware/large-memory-mode-check.md) - The EBOOT's memory-size flag only asks the custom firmware for the extended user memory; detect the 24 MB fallback at start and exit with a message; the volatile 4 MB block can hold GE lists, textures and the movie decoder if it is locked and released correctly.
- [Media Engine rules](hardware/media-engine-rules.md) - The second CPU pays off for audio, but only with explicit cache handling, no libc, a sleep handler and step-wise qualification.
- [Memory-bound CPU: the instruction cache dominates](hardware/memory-bound-cpu-icache.md) - A large translated program on the PSP stalls on instruction-cache misses; code size and layout are speed.
- [Open-file limit on the memory stick](hardware/memory-stick-open-file-limit.md) - Keep at most about 8 files open; on an open failure close the least recently used file and retry.
- [Overclock only through the custom firmware's own call, at the very start, with a crash-safe fallback](hardware/overclock-cfw-api-only.md) - Above 333 MHz, only the custom firmware's own clock call at the first line of main() survived; writing the PLL register yourself switched the console off every time; keep a state file that steps the clock down after a crash.
- [Power-offs around exit are kernel hangs: fix what you can, measure with five runs per arm](hardware/power-off-around-exit.md) - A PSP that switches itself off is usually a kernel hang the watchdog ends; remove the known causes (handlers over freed memory, automatic exits, clock writes) and judge exit fixes over at least five runs per variant.
- [An on-device profiler: zones, per-thread clocks, hashed sampling, counters from a kernel thread](hardware/profiler-on-device.md) - Wrap translated functions in zones with one clock per guest thread, sample short hot functions with a hashed 1-in-N choice, keep everything integer, read the hardware counters only from a kernel thread, and report the profiler's own cost.
- [A streaming budget below the working set thrashes every frame](hardware/streaming-budget-thrash.md) - Size the game heap as resident data + streaming budget + 1.6 to 2 MB headroom, from load counters.
- [Textures: keep the palette indices, convert at load; fetch traffic is the cost](hardware/texture-fetch-traffic.md) - Convert PS2 PAL4/PAL8 textures in place at load time (un-swizzle + GE swizzle, CLUT reorder, alpha doubling); what costs frame time is texture fetch traffic on the bus, so half-resolution or generated mipmaps pay, pre-converted files do not.
- [Where a frame goes on the PSP: the main CPU is the wall](hardware/where-the-frame-goes.md) - In a large translated 3D game the main CPU (memory-bound translated code) sets the frame time; the GE and the Media Engine's bus traffic were not the limit; reach 30 fps by doing less game work per frame.

## translation (analysis and translation of PS2 code)

- [Translator levers measured on hardware: code size beats instruction count](translation/backend-levers-measured.md) - On the I-cache-bound PSP, back-end levers that remove code win; instruction-count savings that grow code lose; every lever needs a hardware A/B.
- [Boot to the first blocker, strict](translation/boot-to-first-blocker.md) - Run strict, fix the first fatal line, look past it only with named experiment switches that never become defaults.
- [Function discovery and jump tables](translation/function-discovery-jump-tables.md) - Strong starts cut functions, weak starts do not; recover jump tables backwards from the jr to its guard.
- [The pipeline: boot program to EBOOT, host first](translation/pipeline-host-first.md) - Translate offline (R5900 -> C), replace the OS and hardware by name (HLE), reach the main loop on a PC host build first, then build for the PSP; everything game-derived is generated on the user's PC.
- [The R5900 FPU is not IEEE](translation/r5900-fpu-not-ieee.md) - Clamp operands, round toward zero, flush, no fused multiply-add; the PSP FPU uses denormal inputs, so clamps stay.
- [Width and liveness bugs show only when the game boots](translation/width-liveness-bugs-at-boot.md) - Narrowing and liveness must be whole-program and run to a fixpoint; syscalls, HLE calls, tail calls and hooks read more than the guest body shows.

## hle (replacing PS2 kernel, libraries and devices)

- [IOP replies must be exact and in step with virtual time](hle/iop-replies-exact-virtual-time.md) - Whatever stands in for a game's IOP module must answer every RPC exactly as the original, at the same virtual time.
- [Reference runs: find the first divergence](hle/reference-run-first-divergence.md) - Run the original in PCSX2 and the port to the same point; the first register or memory difference is the bug.
- [Sound: the IOP driver in lockstep with virtual time, samples rendered on the Media Engine](hle/sound-driver-lockstep-me.md) - Run the game's IOP sound driver (recompiled or modelled) on the game thread in step with virtual time, mix through an integer SPU2 model, stretch the output when the game runs below real time, and move sample rendering to the Media Engine.
- [Virtual time and pacing: follow the real clock, forgive lag](hle/virtual-time-pacing.md) - Advance virtual time by fixed charges, honour the game's video mode and frame limiter, let virtual time follow the real clock while the guest works (forgive lag instead of paying it back), pace the boot in real time, and freeze time during movies.
- [VU0: macro ops exact by rule, micro programs with static timing](hle/vu0-macro-micro.md) - Translate VU0 macro instructions inline with the VU's own arithmetic rules; translate VU0 micro programs to C with flag and Q timing resolved at translation time; never use the VFPU for results the game reads.

## workflow (testing, deploying, measuring, working with the user)

- [A/B sets with a control and a control-again](workflow/ab-sets-control-again.md) - Compare variants on the PSP only against two control runs; their difference is the drift.
- [Working with several agents: a lead session, specialised agents, reports with a resume point, gates](workflow/agent-team-workflow.md) - One lead session owns the plan, shared files and the memory stick; each specialised agent owns named paths, writes a report with a WORK IN PROGRESS section, keeps backups, builds in its own folders and proves results with the gates before anything counts.
- [Copy to the memory stick file by file and verify md5](workflow/deploy-md5-verify.md) - The PSP's USB link drops mid-write: copy file by file, hash every file on both sides, verify again at the end.
- [Verify the log you read](workflow/log-path-verification.md) - Before analysing a log, prove it is the run of the build you deployed: build number, run sequence, folder.
- [One-run interleaved A/B: up to four variants in one boot, a verdict with a confidence interval](workflow/one-run-interleaved-ab.md) - Switch run-time options between variants every few iterations inside one run, in seeded random block order, and decide by paired window differences with a sign-test interval; it removes the game-path noise that separate folders suffer from.
- [PPSSPP gives booleans, the PSP gives numbers](workflow/ppsspp-booleans-hardware-numbers.md) - Use PPSSPP to answer does it boot, render and play; take every timing and memory number from the real PSP.
- [What the reference port reached, honestly](workflow/reference-port-results.md) - A large open-world 3D PS2 game reached about 30 fps indoors and 17-21 fps outdoors on a PSP-3000 at 333 MHz (about 9 % more at 365 MHz), starting from about 7 fps, with reduced density and draw distance; quote these numbers, not "full speed".
