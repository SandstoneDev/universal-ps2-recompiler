# HLE: replace what the PSP does not have

A hook replaces one guest function with C. Generic behaviour (a Sony library function, a syscall, a device) belongs in
the core (`hle/core/`, public); the game's own functions belong in the pack's `src/` (local). Write HLE from the
observed behaviour and public hardware facts; a hand translation of the game's own code is derived from the game and
stays local forever (legal-guard).

## 1. Hooks and the hook list

```
HOOK(000a1000, sceSifCallRpc)      /* a Sony library function: the core implements it by name */
HOOK(000a1100, my_frame_end)        /* a game function: the pack implements HLE_FN(my_frame_end) */
TRACE(000a1200, my_main_loop, 1)    /* original runs, logged; flag 1 = boot milestone */
```

(Addresses above are placeholders.) In C: `HLE_FN(name) { ... GUEST_FN(name)(c); ... }` - the original stays callable.
The names the core implements are the `HLE_SCE(...)` definitions in `hle/core/*.c`; see `hle/core/hle.h` for the pack
interface (`hle_pack_boot_init`, `hle_pack_iop_init`, `hle_pack_vcallms`, `hle_pack_trace`). Labels of the game's own
functions are neutral descriptions of what they do, never names taken from the game. **Translate again after every
change of the hook list.**

What the core already provides (extend it generically, never with game special cases): EE kernel (threads with strict
priorities and no time slicing, semaphores, sleep/wake-up, alarms, interrupt and DMA handlers at safe points), the
syscalls compiled games use, hardware registers and DMA on virtual time, SIF RPC by server ID, files and sector reads
on the user's extracted disc, controller, memory card as a folder.

## 2. The IOP side (sound, streaming)

The game's EE code talks to its IOP modules through SIF RPC and usually reads state back every frame. Whatever
answers must answer **exactly and in step with virtual time**.

- Generate the module on the user's PC: `python -m ps2rc.iop gen MODULE.IRX -o <work>/module.c --sym NAME`
  (`info` / `list` first). The recompiler refuses what it cannot translate exactly instead of guessing. The output is
  game-derived: it lives in the work directory and is never committed; the pack only binds it (server ID, memory,
  SPU2 connection) and names the generator in its `[convert] generators`.
- Fingerprint every reply (a hash per reply, logged every 1024 RPCs) so the host, PPSSPP and the PSP can be compared.
- Validate against PCSX2 field by field before you trust it.

## 3. VU0 micro programs

`python -m ps2rc.vu.micro_gen --elf BOOT --chain ADDR --entries A,B --sym NAME -o <work>/vu0_prog.c` follows the DMA
chain that uploads the program, resolves the pipeline timing at translation time and writes one C function per entry
point plus a check that the uploaded code is the expected one. It refuses VU data memory, XGKICK, the EFU and some flag
instructions; such a program needs a replacement written from its observed behaviour. Check that EE code does not
touch the VU0 between the start and the read of the results; verify against PCSX2's VU0 interpreter with vectors that
cover every branch path.

## 4. Rendering: choose the boundary with the user

The PS2 draws through the GS, fed by VIF and VU1; the PSP has none of them. Replace the renderer at its **lowest stable
software boundary** - usually the middleware's or engine's device-driver layer - and draw with the GE; keep the
engine's own render logic translated. Rejected in practice: emulating the VU1 (exact pipeline latencies, the CPU does
all transform and lighting); converting GIF packets to GE commands (still needs the VU1); replacing high up at the
game's own render functions (many entry points, behaviour lost).

This is the biggest per-game decision: present the candidate boundary (which functions, how many hooks, what stays
translated) to the user before writing it. Order of work: hooks that only log; the host software rasteriser and frame
dumps compared with PCSX2 screenshots; the GE path for 2D; then 3D. Keep the translated driver running behind the
hooks until the GE path is validated, then skip it with a switch. GE rules: `knowledge/hardware/ge-display-list-safety.md`.

## 5. Reference runs (the ground truth)

When the port and the original disagree, run the original in PCSX2 (BIOS dumped from the user's own console) and find
the **first divergence**:

1. Bring both to the same point: a breakpoint on the function's entry in PCSX2; a TRACE or a log line in the port.
2. Record registers and the memory the function reads, on both sides.
3. Step or run to the function's return; record the result and the memory it wrote.
4. The first register or memory difference is the place of the bug: an argument wrong at entry means the caller
   (or the translation of the caller); a correct entry and a wrong result means the function or its HLE.
5. Save a state before risky experiments; compare whole structures, not single words.

`python -m ps2rc.oracle setup` and `python -m ps2rc.oracle run <elf> --done-addr ADDR [--read ADDR N] [--interp]` run
small programs in PCSX2 over its PINE interface (bit-exact tests). PCSX2's interpreter and recompiler disagree on some
FPU edge cases: compare against both. A debugger front-end for PCSX2, if the user has one, is optional; ask before
connecting to anything.

## 6. Before you write the fix (attack your own proposal)

Answer in one sentence each: what failed; which layer; why the original works; which single fix tool; what it can
break (which other callers, which gates). Then argue against it: is it a symptom patch (an address special case in the
core)? does it hide a crash that becomes silent corruption? did you read the code or remember it? If the answer to any
is weak, go back to the reference run.
